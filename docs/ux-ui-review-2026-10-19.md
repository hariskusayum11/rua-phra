## ข้อสรุป

เว็บไซต์มีภาพและบุคลิกที่น่าดูแล้ว ภาพถ่ายเรือจริงและมือช่างเป็นจุดแข็งที่สุด สีเขียวเข้ม ครีม และสีดินทำให้ภาพหลากสีเด่นโดยไม่ต้องเพิ่มการตกแต่งมาก แต่การเรียบเรียงยังให้อารมณ์ข้อความประชาสัมพันธ์มากกว่าการอ่านเรื่องจากพื้นที่จริง คำคมซ้ำหลายช่วง ข้อมูลสาธิตปะปนกับเนื้อหาจริง และข้อความรอเก็บข้อมูลถูกจัดวางเด่นเกินความสำคัญ

คำว่า “ดูเป็น AI” ในรายงานนี้หมายถึงความรู้สึกจากรูปแบบภาษาและการจัดองค์ประกอบ ไม่ใช่การพิสูจน์ว่าใครเป็นผู้เขียน

ควรแก้ความสอดคล้องของข้อมูล ลดความยาว และปรับน้ำเสียงก่อนเปลี่ยนธีมใหม่

## ขอบเขตและหลักฐาน

- เปิดเว็บสาธารณะจริงด้วย Edge แบบ headless ไม่ได้ใช้เฉพาะการอ่านโค้ด
- เดสก์ท็อป 1440 × 1000: หน้าแรก, /craft, /learn, /competition, /about, /exhibition, เรือวัดรัตนาราม 2568, ขั้นเตรียมวัสดุ และหน้ารวมบทเรียนของหลักสูตร
- มือถือ 390 × 844: หน้าแรก, /craft, /learn และหน้าเรือ
- ตรวจเมนูและการเปิดจุดสำรวจหน้าแรกเพิ่มเติมที่ความกว้าง 320 และ 768 พิกเซล
- ใช้ axe ตรวจสถานะหน้าแรก /craft /learn และหน้าเรือทั้ง desktop/mobile: ไม่พบ violation ในชุดกฎที่รัน แต่ไม่ได้หมายถึงผ่าน accessibility ทุกกรณี โดยเฉพาะ interaction หลังเปิด panel
- ไม่พบหน้าเว็บล้นแนวนอนในสถานะที่วัด
- ไม่มีการเปลี่ยนโค้ดแอป ข้อมูลฐานข้อมูล หรือ deploy ในการตรวจครั้งนี้
- เวอร์ชัน live กับไฟล์ใน workspace มีรายละเอียดต่างกัน เช่น รูปแบบ footer และสีบางส่วน รายงานจึงอ้างอิงหน้าจอ live เป็นหลัก

## สิ่งที่ควรรักษา

1. **ภาพถ่ายจริง** — ภาพเต็มลำ ภาพมือช่าง และภาพเครื่องมือให้รายละเอียดที่งานกราฟิกทั่วไปทดแทนไม่ได้
2. **ชุดสีและความเรียบของโครงหน้า** — ไม่มีปัญหา excessive cards หรือ gradient ตกแต่งเป็นประเด็นหลัก overlay บนภาพมีหน้าที่ช่วยอ่านข้อความ
3. **ชื่อโครงการและ tagline** — “เรือพระเล่าเรื่อง” และ “ทุกลายมีเรื่อง ทุกเรื่องมีคนส่งต่อ” จำง่าย เก็บไว้เป็นแกนหลักได้
4. **ภาพระยะใกล้หลังแตะ hotspot** — ช่วยให้เกิดการเรียนรู้จริงและเป็นฟีเจอร์ที่แตกต่างจากเว็บประชาสัมพันธ์
5. **เมนูมือถือหลัง animation จบ** — ตัวอักษรชัด พื้นหลังทึบและแยกจากหน้าเว็บ ไม่พบปัญหาข้อความซ้อนค้าง ภาพที่จับกลาง animation ไม่ใช้เป็นหลักฐานข้อบกพร่อง
6. **การระบุสถานะข้อมูล** — ควรเก็บความโปร่งใสไว้ แต่ย้ายให้เป็นข้อมูลประกอบแทนการให้เป็นข้อความหลัก

## ต้องปรับก่อน — ความน่าเชื่อถือและความเข้าใจ

### 1. ข้อมูลขั้นตอนกับรายการเครื่องมือไม่สอดคล้องกัน

ใน /craft ขั้น “เตรียมวัสดุ” อธิบายการจัดเหล็กตอกและค้อนไม้ แต่รายการเครื่องมือแสดง “ดินสอร่างแบบ” ขั้น “ตอกลาย” ก็แสดงดินสอเช่นกัน ส่วนวัสดุยังมีชื่ออย่าง “กระดาษสำหรับทดลอง” และ “วัสดุยึดติดสำหรับทดลอง”

หน้ารายละเอียดขั้นเตรียมวัสดุยังมีภาพ placeholder ร่วมกับภาพถ่ายจริง และความสัมพันธ์ไปยังช่างที่ระบุว่าเป็นบุคคลสมมติสำหรับทดสอบระบบ

**ผลต่อผู้ใช้:** อ่านแล้วไม่แน่ใจว่ารายการอุปกรณ์เป็นความรู้ที่ใช้ได้จริง หรือเป็นเพียงโครงร่างระบบ การปรับสีหรือฟอนต์ไม่สามารถแก้ความคลาดเคลื่อนนี้ได้

**แนวทาง:** ตรวจ relationship ของแต่ละขั้นตอนกับวัสดุ เครื่องมือ เทคนิค และช่างทีละรายการ ใช้เฉพาะข้อมูลที่รองรับได้ หากยังไม่ยืนยันให้ระบุสั้น ๆ ว่า “รายการอุปกรณ์อยู่ระหว่างตรวจสอบ” แทนการเติมข้อมูลทดลองให้ครบทุกช่อง

### 2. ข้อความสถานะถูกแสดงเหมือนคำพูดของช่าง

หน้า /boats/rua-phra-wat-rattanaram-2568 แสดงข้อความนี้เป็นตัวใหญ่ สีเด่น และมีเครื่องหมายอัญประกาศ:

> “ยังไม่ได้บันทึกแนวคิดของเรือลำนี้ รอการสัมภาษณ์ช่างผู้ออกแบบ”

หน้าแรกก็นำข้อความเดียวกันไปวางเด่นใต้คำว่า “แนวคิด”

**ผลต่อผู้ใช้:** สิ่งที่สะดุดตาที่สุดกลายเป็นงานที่ยังไม่เสร็จ และรูปแบบ quote ทำให้สถานะของข้อความผิดความหมาย

**แนวทาง:** ใช้ชื่อวัด ปี ภาพเรือ และรายละเอียดที่บันทึกได้เป็นเนื้อหาหลัก ย้ายข้อความนี้เป็นหมายเหตุขนาดปกติ เช่น “แนวคิดการออกแบบ: อยู่ระหว่างสัมภาษณ์ช่าง” ไม่สร้างคำคมหรือเรื่องเล่ามาแทนข้อมูลที่ยังไม่มี

### 3. ผลงานสาธิตและบทเรียนสาธิตยังปรากฏเหมือนส่วนที่พร้อมใช้งาน

หน้าแรกแสดงผลงานผู้เรียน 4 ชิ้นเป็นภาพดอกไม้แบบ placeholder ที่ยังมีคำว่า PLACEHOLDER และชื่อผู้เรียน ก/ข/ค/ง ส่วนการ์ดบทเรียนชวนเริ่มเรียน แต่สถานะ “ยังไม่ใช่บทเรียนจริง” ปรากฏชัดกว่าเมื่อเข้าหน้า /learn

**แนวทาง:** แยกข้อมูลสาธิตออกจากพื้นที่จัดแสดงหลักของเว็บไซต์สาธารณะ หากจำเป็นต้องเปิดให้ทดลอง ให้ติดป้าย “ตัวอย่างบทเรียน — ข้อมูลสาธิต” ตั้งแต่ก่อนคลิก สำหรับผลงานที่ยังไม่มีจริง ให้ลดเหลือข้อความสั้น ไม่ต้องใช้พื้นที่แกลเลอรีเต็มช่วง

### 4. ข้อความภาพกับข้อมูลช่างมีความขัดแย้ง

ส่วนช่างแสดง “ในภาพ: พี่อัฐ วัดรัตนาราม” แล้วตามด้วย “ยังไม่ได้บันทึกชื่อและคำบอกเล่าของช่าง” ทั้งที่มีชื่อที่ใช้เรียกอยู่แล้ว

**แนวทาง:** ระบุให้ตรงสิ่งที่ขาด เช่น “พี่อัฐ · ช่างวัดรัตนาราม” และ “ประวัติและบทสัมภาษณ์อยู่ระหว่างการบันทึก” หลังตรวจว่าชื่อเรียกนี้ถูกต้องและใช้เผยแพร่ได้

## UX/UI ที่ควรปรับ

### หน้าแรกยาวและเฉลี่ยน้ำหนักให้ทุกหัวข้อมากเกินไป

วัดได้ประมาณ 17,055 px ที่ 1440 × 1000 และ 17,469 px ที่ 390 × 844 หรือประมาณ 17 และ 21 เท่าของความสูง viewport ตามลำดับ ไม่ใช่จำนวนครั้งที่ผู้ใช้ต้องปัดจริง

- คลังเรือเริ่มราวตำแหน่ง 3,146 px บน desktop
- จุดสำรวจที่โต้ตอบได้เริ่มราว 4,907 px บน desktop และ 4,048 px บนมือถือ
- ส่วน “ศิลปะ / ศรัทธา / เรื่องเล่า / ภูมิปัญญา” ใช้พื้นที่มาก แต่ให้ข้อมูลใหม่ค่อนข้างน้อย
- กระบวนการ ช่าง ลวดลาย และบทเรียนมี intro ขนาดใหญ่เกือบทุกช่วง จังหวะจึงซ้ำกัน

**แนวทาง:** ให้ฟีเจอร์แตะสำรวจเรืออยู่ภายในช่วงต้น ลดหน้าแรกเหลือราว 6–7 ส่วน เนื้อหาเชิงรายละเอียดใช้หน้ารอง ลดระยะห่างที่ทำหน้าที่เพียงคั่นคำคม ควรเริ่มทดลองลดความยาวประมาณหนึ่งในสามถึงครึ่ง แล้วประเมินการอ่านจริง

ลำดับที่เสนอ:

1. ภาพเรือ + ชื่อโครงการ + คำอธิบายว่าเป็นเรือพระจากที่ไหน + ปุ่มสำรวจเรือ
2. เรือที่เลือกไว้และจุดสำรวจที่กดได้ทันที
3. ภาพงานกระดาษและขั้นตอนตัวอย่าง 3 ขั้น
4. ลวดลายเด่นที่มีรายละเอียดพร้อม
5. ช่างและคำบอกเล่าที่มีหลักฐานรองรับ
6. ทางเข้าบทเรียน หรือวิดีโอจากพื้นที่ ตามความพร้อมของเนื้อหา
7. ที่มาโครงการและหน่วยงาน

### Hero บนมือถือครอปจนมองไม่เห็นเรือเต็มลำ

ภาพแนวนอนถูกใช้เป็นพื้นหลังสูง 844 px ในความกว้าง 390 px ทำให้เห็นท้องฟ้าจำนวนมากและเห็นเรือเฉพาะตรงกลาง ภาพที่ได้ดูนุ่มและไม่บอกทรงเรือชัด

**แนวทาง:** ทำกรอบภาพเฉพาะมือถือ อาจใช้ภาพเต็มลำในอัตราส่วนแนวนอนและวางข้อความแยกด้านล่าง หรือเลือกภาพแนวตั้งที่มีจุดสนใจเหมาะจริง ปรับการเลือกความละเอียดภาพตามพื้นที่หลัง crop อย่าแก้ด้วยการเพิ่ม overlay จนรายละเอียดมืดกว่าเดิม

### จุดแตะบนเรือทับกันบนจอเล็ก

แม้ปุ่มมีพื้นที่ 44 × 44 px บนหน้าแรก แต่ที่ 390 px จุด 02 กับ 03 มีระยะห่างแนวตั้งประมาณ 28 px ทำให้พื้นที่แตะทับกัน ที่ 320 px ระยะลดเหลือประมาณ 22 px และจุด 04 อยู่ใกล้กันด้วย

**แนวทาง:** คงขนาดพื้นที่แตะ เพิ่มรายชื่อส่วนประกอบใต้ภาพเป็นทางเลือก และพิจารณาให้ขยายภาพหรือแยกตำแหน่งป้ายด้วยเส้นชี้ อย่าแก้โดยลดปุ่มจนแตะยาก

### ประสบการณ์ panel หน้าแรกกับหน้ารายละเอียดไม่เหมือนกัน

หน้าแรกเปิด bottom sheet โดย focus ยังอยู่ที่ hotspot ด้านหลัง ส่วนหน้ารายละเอียดใช้ dialog ที่มี backdrop และภาพพื้นหลังเบลอ รูปแบบปุ่มปิดก็ไม่เหมือนกัน

**แนวทาง:** ใช้รูปแบบ panel และพฤติกรรมเดียวกัน ตัดสินให้ชัดว่าเป็น modal หรือ non-modal ถ้าเป็น modal ต้องจัดการ focus, การปิดด้วย Escape และคืน focus ให้ครบ ตรวจด้วยคีย์บอร์ดหลังเปิด sheet อีกครั้ง เพราะผล axe ในสถานะปิดยังไม่ครอบคลุมกรณีนี้

### ภาษาไทยอ่านได้ แต่ควรลดความต่างระหว่างหัวเรื่องกับเนื้อหารอง

ตัวหลักและการเว้นบรรทัดอยู่ในทิศทางที่ดี แต่หัวข้อ desktop หลายจุดประมาณ 63 px ขณะที่คำอธิบายหรือ metadata อยู่ราว 13–17 px ทำให้ผู้ใช้รับอารมณ์ของหัวเรื่องก่อนข้อมูลจริงอยู่เสมอ

**แนวทาง:** เก็บขนาดใหญ่ให้ hero และหัวเรื่องหลักไม่กี่จุด เนื้อหาอ่านต่อเนื่องใช้ประมาณ 17–18 px บนมือถือ ข้อมูลประกอบสำคัญไม่ควรเล็กเท่าหมายเหตุทั้งหมด หลีกเลี่ยงการตัดบรรทัดบังคับที่ทำให้คำว่า “คนรุ่นใหม่” หรือชื่อส่วนประกอบแยกอย่างฝืนสายตา

### เมนูและชื่อทางเข้าควรบอกสิ่งที่เกิดขึ้นหลังคลิก

“เรื่องเล่าเรือพระ”, “อ่านเรือพระ”, “สำรวจเรื่องราว” และ “เริ่มสำรวจเรื่องราว” มีความหมายใกล้กัน แต่ไปคนละตำแหน่ง ขณะที่ “คลังลวดลาย” ในเมนูพากลับไปยัง section ของหน้าแรก

**แนวทาง:** ใช้ “ชมเรือพระ”, “สำรวจส่วนประกอบ”, “ดูวิธีทำงานกระดาษ”, “ดูบทเรียน” ให้สัมพันธ์กับปลายทาง แยกชื่อหมวดเนื้อหาออกจากคำเชิญชวนเชิงกวี

## ภาษาแบบใดทำให้รู้สึกเป็น AI

ไม่ใช่การมีคำสวยเพียงประโยคเดียว แต่เป็นการใช้รูปแบบเดิมต่อกันหลาย section:

- “มากกว่าความงาม”
- “จากการมองเห็น สู่การลงมือทำ”
- “ภูมิปัญญาไม่ได้อยู่เพียงในตำรา แต่อยู่ในคน”
- “เรือพระไม่ได้มีชีวิต เพราะถูกเก็บไว้”
- “ความหมายที่ซ่อนอยู่”
- “ตีความและสร้างสรรค์ของคนรุ่นใหม่”

เมื่อข้อความเหล่านี้อยู่รวมกัน เว็บจะเหมือนบทนำสารคดีหลายบทต่อกัน มากกว่าการพบข้อมูลเฉพาะของเรือแต่ละลำ ควรเก็บ tagline หลักไว้หนึ่งชุด แล้วเปลี่ยนส่วนอื่นให้บอกว่าใคร ทำอะไร ใช้อะไร ที่ไหน หรือผู้ใช้จะเห็นอะไร

ไม่ควรเขียนว่า “ล้วนอยู่ในตัวช่าง ไม่ได้อยู่ในตำรา” หรือ “ไม่ได้เกิดจากการพิมพ์” ในลักษณะเหมารวม หากยังไม่มีหลักฐานพอให้กล่าวเช่นนั้น การบรรยายสิ่งที่เห็นและบันทึกไว้ตรง ๆ น่าเชื่อถือกว่า

## ตัวอย่างปรับข้อความ

เป็นร่างบรรณาธิการ ต้องทวนชื่อเรียกและข้อเท็จจริงกับข้อมูลจริงก่อนเผยแพร่

| ตำแหน่ง / ข้อความปัจจุบัน | ข้อความเสนอ |
| --- | --- |
| คำอธิบาย hero ที่เน้นคำว่าเรื่องราว/ภูมิปัญญา/ส่งต่อซ้ำ | ชมเรือพระจากวัดต่าง ๆ ในอำเภอปากพะยูน ดูลายกระดาษใกล้ ๆ และติดตามขั้นตอนที่ช่างทำ |
| เรือพระปากพะยูน มากกว่าความงาม | รู้จักเรือพระปากพะยูน |
| สำรวจเรื่องราว | สำรวจเรือพระ |
| ค้นพบวิธีสร้าง | ดูขั้นตอนทำลายกระดาษ |
| แตะจุดต่าง ๆ บนเรือ เพื่อค้นพบความหมายที่ซ่อนอยู่ในแต่ละส่วน | แตะจุดบนภาพเพื่อดูชื่อส่วนประกอบและภาพระยะใกล้ |
| ภูมิปัญญาไม่ได้เกิดขึ้นในขั้นตอนเดียว | 7 ขั้นตอนงานกระดาษบนเรือพระ |
| ภูมิปัญญาไม่ได้อยู่เพียงในตำรา แต่อยู่ในคน | ดูช่างตอกลายกระดาษที่วัดรัตนาราม |
| จากการมองเห็น สู่การลงมือทำ | เริ่มรู้จักลายกระดาษทีละขั้น |
| “ยังไม่ได้บันทึกแนวคิด…” แบบ quote | แนวคิดการออกแบบ: อยู่ระหว่างสัมภาษณ์ช่าง — แสดงเป็นหมายเหตุ |
| ฟังเรื่องจากช่าง + ไอคอน Play แต่ยังไม่มีเสียง | บทสัมภาษณ์อยู่ระหว่างการจัดทำ — ไม่จัดรูปแบบเป็นปุ่มเล่น |
| ชมผลงานทั้งหมด · เปิดพร้อมระบบเรียนรู้ | ซ่อนทางเข้าที่ยังไม่พร้อม หรือระบุสถานะเป็นข้อความธรรมดา |

ข้อความในหน้าเกี่ยวกับโครงการ เช่น “ความเงียบจะถูกอ่านว่ายืนยันแล้ว เราจึงไม่ปล่อยให้เงียบ” ควรปรับเป็น “เนื้อหาที่ยังไม่ผ่านการตรวจสอบจะระบุสถานะไว้ในแต่ละหน้า” สั้นกว่าและทำให้ผู้อ่านเข้าใจวิธีใช้งานข้อมูลทันที

## ลำดับดำเนินงาน

1. ตรวจและแยกข้อมูลสาธิตที่ยังเชื่อมกับเนื้อหาจริง โดยเฉพาะเครื่องมือ ช่าง ภาพขั้นตอน และผลงานผู้เรียน
2. ย้ายข้อความรอเก็บข้อมูลออกจากตำแหน่ง quote/heading และทำให้สถานะสาธิตเห็นก่อนคลิก
3. ปรับภาพ hero มือถือและพื้นที่แตะ hotspot ที่ทับกัน
4. ลดความยาวหน้าแรกและย้ายจุดสำรวจขึ้นมาใกล้ส่วนต้น
5. เกลาภาษาทั้งเว็บ ลดคำคมซ้ำ เปลี่ยน CTA ให้บอกปลายทาง
6. ทำ panel สองจุดให้มีรูปแบบและการจัดการ focus สอดคล้องกัน แล้วทดสอบการอ่านและแตะจริงอีกครั้ง
